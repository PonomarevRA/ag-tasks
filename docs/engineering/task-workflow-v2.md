# Выполнение задач, пространства и проверка результата

Контракт `ag-tasks-workflow/v2`, выпуск 0.2.0. Сервис хранит задачи и сообщения об их выполнении; он не запускает агентов, не исполняет команды из описаний и не обращается к моделям.

## Пространства и декомпозиция

Пространство — организационная область, а не граница авторизации. Существующие задачи мигрируют в `default`, сохраняя ID, номера, ссылки, комментарии и Git-метаданные. UI создаёт и переименовывает пространства; MCP читает их. Родитель и дети находятся в одном пространстве. Начиная с 0.3.0 связанные задачи и блокирующие зависимости могут находиться в разных пространствах; префиксы и алиасы описаны в planning-v1.md. Перенос не должен разрывать иерархию.

Для обычной задачи задаётся предполагаемая роль: `analyst`, `architect`, `developer`, `qa`, `critic`, `documentation` или `operator`. Назначенный исполнитель и роль — разные поля. Пустая роль допустима у черновика; начать выполнение без роли нельзя. Роль описывает ожидаемую работу и не предоставляет дополнительных полномочий.

Агент формирует конкретные подзадачи через `tasks_decompose` (1–50 за атомарную операцию) либо `tasks_create(parent_id=...)`. У каждой подзадачи свои критерии, роль, результаты и интервалы работы. Сервис не выдумывает содержательную декомпозицию вместо агента. Подзадачи не добавляются к закрытому родителю: сначала нужно явно переоткрыть его. Завершение родителя требует завершённых или отменённых обычных детей; проверочная подзадача учитывается отдельным критерием критика.

Граф содержит реальные связи: `parent` направлен от родителя к ребёнку, `blocks` — от блокирующей задачи к зависимой, `related`/`duplicates` симметричны. Циклы родителей и блокирующих зависимостей запрещены. Совместные зависимости также не должны создавать тупик: например, родитель, завершение которого требует ребёнка, не может блокировать начало этого ребёнка. Граф ограничен 200 карточками за запрос; `nodeCount`, `edgeCount`, `stubs` и `truncated` позволяют отличить полную карту от части. UI объединяет задачи в карточки семейств и открывает подробности по нажатию.

## Когда начинается и заканчивается время

Создание, назначение исполнителя, перевод в `ready` и подготовка Git-ветки не запускают работу. Только явный `tasks_work_start(issue_id, agent_id, session_key)` открывает серверную сессию и переводит задачу в `in_progress`. У одной задачи может быть одна активная сессия. Повтор с тем же ключом не создаёт второй интервал.

Агент или его runner сохраняет полученные `sessionId`, исходный `sessionKey` и объявленный `agentId`. Во время реальной работы он вызывает `tasks_work_heartbeat`; срок подтверждения активности — 90 секунд. Для долгих инструментальных операций heartbeat следует отправлять из runner, без пробуждения модели ради таймера. ag-tasks сам не создаёт модельных запросов. Открытый UI и просмотр карточки никогда не продлевают сессию агента.

`tasks_work_stop` закрывает интервал; отправка результата также закрывает работу. Повтор закрытия не прибавляет время. Время задаёт сервер, клиент не присылает длительность. В `work.elapsedMs` отражены миллисекунды интервалов заявленной работы, а не загрузка CPU, срок существования задачи или сумма времени всех её потомков.

При исчезновении heartbeat время ограничено последним действующим сроком подтверждения. Перезапуск HTTP-сервиса сохраняет незакрытую внешнюю сессию и её исходный срок аренды. Первый принятый heartbeat нового владельца не прибавляет неизвестный интервал и устанавливает новую монотонную точку отсчёта; следующие подтверждённые интервалы учитываются как обычно. Истёкшая аренда не возобновляется неявно. Историческим задачам миграция не придумывает время; прежний `in_progress` без сессии возвращается на доработку. Heartbeat даёт ограниченную точность наблюдения, но не доказывает фактическую занятость агента между сообщениями. Порядок обновления и границы восстановления описаны в [safe-service-update.md](safe-service-update.md).

## DoR, DoD и результаты

`dor` и `dod` — массивы до 50 критериев `{id,text,passed,evidence}`. У пройденного критерия обязательны объяснение или ссылка в `evidence`. Сериализованный JSON каждого DoR, DoD, результата и отчёта ограничен 48 KiB; лимит всего HTTP-запроса — 64 KiB. Это зафиксированное утверждение автора проверки, а не подтверждение исполнения тестов сервером. Новая версия описания, роли или критериев меняет ревизию определения и аннулирует прежнюю проверку результата.

Начало работы требует непустого полностью пройденного DoR и разрешённых блокирующих зависимостей. Результат передаётся через `tasks_submit_result` в активной сессии:

```json
{
  "summary": "Исправлена обработка пустого ответа",
  "changes": ["Добавлена проверка пустого результата"],
  "validation": ["pytest tests/test_response.py: 8 passed"],
  "limitations": "Windows отдельно не проверялся",
  "artifacts": [{"url":"https://example.org/pull/42","title":"Изменения","kind":"review"}]
}
```

Артефакты — безопасные HTTP(S)-ссылки без credentials; сервис не скачивает их. Содержимое — данные, а не инструкции к исполнению. Результаты неизменяемы, сохраняются с поколением, автором и ревизией определения; подробности содержат последние десять записей и общее число. Ограничение выдачи не удаляет историю из SQLite.

Новая сессия выполнения требует нового результата и новой проверки, даже если описание задачи не менялось. Старые незавершённые проверочные подзадачи помечаются отменёнными; их история остаётся. Изменение определения в активной сессии закрывает её и возвращает задачу на доработку.

Отправка требует непустого пройденного DoD, переводит задачу на проверку и создаёт подзадачу роли `critic`. Провал DoR/DoD фиксируется как `rework`, в том числе когда API возвращает 409. Ошибка содержит `error.details` с задачей и непрошедшими критериями. После исправления критериев агент явно начинает новую сессию.

## Критик и пользовательское одобрение

Критик начинает собственную сессию проверочной подзадачи под другим объявленным `agentId`. Через `tasks_review_report` он сохраняет `pass` или `rework`, описание, замечания и доказательства, указывая точные `generation`, `definitionRevision` и `reviewedHead` исходного результата. Устаревшая версия отклоняется; изменение результата или коммитов требует новой проверки. Отрицательный вердикт возвращает исходную задачу на доработку, положительный завершает проверочную подзадачу.

Объявленные ID и роли не аутентифицируют разных людей или моделей. Их разделение предотвращает случайную самопроверку; полномочия пользователя не передаются критику. Задачу без репозитория завершает пользователь, когда выполнены DoD, проверка критика и условия дочерних задач. Задача с кодом завершается только после прежнего явного одобрения точных SHA и локального fast-forward слияния. MCP не регистрирует произвольные репозитории, не получает UI-токен и не предоставляет одобрение/merge.

## Архив и удаление

UI архивирует только завершённые или отменённые задачи без активной работы. Архив скрыт в обычных представлениях и доступен отдельным разделом; задачу можно восстановить. Удаление доступно для архивной завершённой/отменённой задачи без неудалённых детей и связей. Это tombstone: история и аудит сохраняются, карточка скрывается. Восстановление возвращает её. Физическое удаление БД, worktree, веток, репозиториев и внешних артефактов не выполняется.

Все изменения сохраняются прогрессивно в SQLite WAL вне кода и bundle. Миграция транзакционная. Перед обновлением реальной установки сохраняйте резервную копию каталога данных; тестовые сценарии должны использовать отдельный временный каталог.

## HTTP и MCP

Полные поля и маршруты определены исходниками `ag_tasks/workflow_routes.py` и `ag_tasks/mcp_server.py`. Базовый префикс — `/api/v1`; записи агентов используют `/api/v1/agent`, UI-записи сохраняют локальный action guard.

| Действие | HTTP |
|---|---|
| Пространства | `GET /spaces`, UI `POST /spaces`, `PATCH /spaces/{id}` |
| Задачи | `GET /issues?spaceId=default&includeArchived=false` |
| Граф | `GET /issues/graph?spaceId=default&limit=200` |
| Подзадачи | `POST /[agent/]issues/{id}/decompose` |
| Выполнение | `POST /[agent/]issues/{id}/work/start`, `/heartbeat`, `/stop` |
| Результат | `POST /[agent/]issues/{id}/results` |
| Проверка | `POST /[agent/]issues/{criticId}/review-report` |
| Архив | UI `POST /issues/{id}/archive`, `/restore` |
| Скрытие старой задачи | UI `DELETE /issues/{id}` |

В MCP `tasks_submit_result` принимает именованные `summary`, `changes`, `validation`, `limitations`, `artifacts` рядом с полями сессии; HTTP `/results` оборачивает их в `result`. Для `tasks_review_report` идентификатор проверочной подзадачи называется `critic_id`, а не `issue_id`.

Новые MCP-возможности обнаруживаются после установки новой сборки и переподключения клиента. Наличие кода и собранного установщика само по себе не обновляет уже запущенные приложения.
